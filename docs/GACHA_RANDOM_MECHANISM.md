# Gacha 随机机制设计

## 1. 目标与范围

本文定义武器 Gacha 的候选池、六组概率、pickup 分配、十连末位规则，以及管理平台和服务端明文配置格式。

本文同时作为当前服务端实现与验收的约束。实现会修改服务端运行代码和管理平台，但不修改协议，也不会把 Gacha 配置写入主数据。

本设计不包含累计保底、天井、阶梯卡池的额外概率修正，也不改变抽取消耗、重复物品转换和发奖流程。

## 2. 术语

所有随机结果都以武器为基本单位：

- `character_weapon`：赠送角色的武器。武器在主数据中存在有效的关联角色；抽中后同时发放该武器及关联角色。
- `weapon_only`：仅武器。抽中后只发放武器。

武器按可获取范围分为：

- `event`：活动武器，只能从活动商店获取，永不加入 Gacha。
- `standard`：常驻武器，可加入任意武器 Gacha。
- `limited`：限定武器，只能加入配置了匹配限定集合的 Gacha。

“活动武器”描述的是武器的获取渠道，不等同于活动期间开放的限定 Gacha。

## 3. 六个随机组

候选武器按发奖类型与星级划分为六个逻辑组：

| 组 | 类型 | 星级 | 基础权重 | 普通单抽概率 |
| --- | --- | ---: | ---: | ---: |
| `character_weapon_4` | 赠送角色的武器 | 4 | 200 | 2% |
| `weapon_only_4` | 仅武器 | 4 | 300 | 3% |
| `character_weapon_3` | 赠送角色的武器 | 3 | 500 | 5% |
| `weapon_only_3` | 仅武器 | 3 | 1,000 | 10% |
| `character_weapon_2` | 赠送角色的武器 | 2 | 0 | 0% |
| `weapon_only_2` | 仅武器 | 2 | 8,000 | 80% |

基础权重合计为 10,000。该分布沿用现有服务端的 2% / 3% / 5% / 10% / 80% 分布；`character_weapon_2` 仍作为逻辑组保留，但当前权重为 0。

组权重使用非负整数表示，随机选择时不依赖浮点数。普通位置选择组 `g` 的概率为：

```text
P(g) = W(g) / ΣW
```

任何权重大于 0 的组都必须至少包含一个候选武器。服务端不得因为组为空而静默删除该组或重新归一化，否则实际概率会偏离配置和公示概率。

## 4. 配置平台与明文配置

Gacha 配置应加入仓库现有、受 `LUNAR_ADMIN_TOKEN` 保护的 `/admin/` 管理平台。管理平台是主要编辑入口，UTF-8 JSON 文件是服务端读取和发布的最终产物；仍保留直接审阅或手工修复 JSON 的能力。

Gacha 配置与 `.bin.e` 主数据分开保存，例如 `server/config/gacha.json`。保存 Gacha 配置不会重建、改写或重新分发主数据。

### 4.1 主数据生成的武器对照表

管理平台每次读取当前运行中的主数据后，生成一张只读基础信息与可编辑分类合并的武器对照表。每个可抽取的武器进化链只显示根武器一行，避免开发者误把进化后形态加入卡池。

对照表至少包含：

| 字段 | 来源 | 是否可编辑 | 说明 |
| --- | --- | --- | --- |
| 武器 ID | 武器主数据 | 否 | Gacha 配置和随机结果使用的稳定 ID |
| 武器名称 | 当前本地化资源 | 否 | 跟随管理平台当前语言；缺失时显示 `#武器ID` |
| Costume 名称 | 武器—Costume 关联与 Costume 本地化资源 | 否 | 仅赠送 Costume 的武器显示；缺失时显示 Costume ID |
| 属性 | 武器主数据 | 否 | 火、水、风、光、暗 |
| 武器类型 | 武器主数据 | 否 | 小剑、大剑、枪、铳、杖、拳 |
| 星级 | 武器主数据 | 否 | 2、3、4 星 |
| 发奖类型 | 关联关系推导 | 否 | `赠送角色的武器` 或 `仅武器` |
| 获取类别 | Gacha 配置 | 是 | 常驻（默认）、活动或限定 |
| 限定集合 | Gacha 配置 | 是 | 仅获取类别为限定时必填 |

生成关系如下：

```text
根武器 ID
  → 武器主数据：属性、武器类型、星级、进化链
  → 本地化资源：武器名称
  → 武器—Costume 关联：关联 Costume ID
  → Costume 主数据：ActorSkeletonId、AssetVariationId
  → 本地化资源：Costume 名称
```

武器名称和 Costume 名称仅用于帮助开发者识别条目，不写入 `gacha.json`，也不参与运行时判断。名称变化后刷新管理页面即可看到新值，不会造成配置和主数据的名称不一致。

页面应支持按武器 ID、武器名称或 Costume 名称搜索，并分别按获取类别、属性、武器类型和是否赠送角色筛选。星级使用 `★★`、`★★★`、`★★★★` 显示，不再额外显示“分组”列。获取类别和限定集合只支持逐行编辑，不提供批量分类操作。

### 4.2 逐条分类

每件可抽取根武器默认都是 `standard`，无需在配置文件中保存记录。开发者只为需要覆盖默认值的武器选择以下类别：

- `standard`：加入所有武器卡池；这是缺省值，选择后删除该武器的覆盖记录。
- `event`：永不加入卡池，只能由活动商店等其他系统发放。
- `limited`：必须再选择一个限定集合，只加入匹配该集合的卡池。

`character_weapon` 和 `weapon_only` 由武器—角色关联自动推导，不允许在管理平台手工修改。这样可以避免开发者把“获取类别”和“发奖类型”混淆，也能保证抽取与实际发奖一致。

页面不存在“未分类”状态。主数据已明确排除出 Gacha 的根武器由服务端自动视为活动，不显示在配置页面中，也不写入 `gacha.json`；其他根武器没有配置记录时显示为常驻。开发者手工设置的活动武器仍作为显式覆盖显示并保存。

限定集合由稳定键和显示名称组成，例如稳定键 `example_limited_01`、显示名称“示例限定 01”。修改显示名称不影响武器和卡池之间的匹配。

### 4.3 按卡池配置 pickup

管理平台从当前 Gacha 目录生成卡池列表，每行显示 Gacha ID、本地化名称、开放时间和配置状态。以服务端 API 实际使用的 Gacha ID 作为配置键。

选择一个卡池后，页面分为“可抽取武器”和“已选 pickup”两个区域：

1. 先选择该卡池允许的限定集合；常驻武器自动可用，活动武器始终不可用。
2. 从最终候选池中勾选 pickup。活动武器和不匹配的限定武器不得勾选，并显示不可用原因。
3. 候选武器区支持按 ID、武器名或 Costume 名搜索，并按星级、属性、武器类别和是否赠送角色筛选。
4. 页面暂不展示概率预览；发布时仍校验普通位置与十连末位的候选池，空正权重组或全组 pickup 会禁止发布。

每个主数据卡池在页面中都有配置入口。未建立卡池配置、`pickupWeaponIds` 字段缺失或数组为空时，均按“仅常驻、无 pickup”处理，并明确显示为“使用默认配置”，而不是让开发者猜测其状态。

`pickupWeaponIds` 的数组顺序仅作为推广页面的稳定展示顺序；概率计算仍按集合处理。页面应允许拖动或使用上移、下移调整展示顺序。

### 4.4 发布配置格式

JSON 的 `weapons` 使用稀疏覆盖结构：没有出现的武器默认常驻，只保存活动和限定覆盖，使人工审阅聚焦于特殊条目：

```json
{
  "version": 1,
  "sourceMasterDataHash": "sha256:example",
  "groupWeights": {
    "characterWeapon": {
      "2": 0,
      "3": 500,
      "4": 200
    },
    "weaponOnly": {
      "2": 8000,
      "3": 1000,
      "4": 300
    }
  },
  "limitedSets": {
    "example_limited_01": {
      "displayName": "示例限定 01"
    }
  },
  "weapons": {
    "310101": {
      "availability": "event"
    },
    "320001": {
      "availability": "limited",
      "limitedSet": "example_limited_01"
    }
  },
  "banners": {
    "614": {
      "limitedSets": ["example_limited_01"],
      "pickupWeaponIds": [320001, 310001]
    }
  }
}
```

配置含义：

- `sourceMasterDataHash`：发布时所依据的主数据内容哈希，用于提示配置是否落后于当前主数据，不参与概率计算。
- `groupWeights`：六组基础权重。初始值使用第 3 节所列分布。
- `limitedSets`：限定集合的稳定键和开发者可读显示名称。
- `weapons.*.availability`：该武器对默认常驻行为的覆盖，只需保存 `event` 或 `limited`；旧配置中的显式 `standard` 在保存时自动省略。
- `weapons.*.limitedSet`：限定武器所属的唯一限定集合；其他类别不得填写。
- `banners`：以服务端 API 使用的 Gacha ID 为键的卡池配置。
- `banners.*.limitedSets`：该卡池匹配并可加入候选池的限定集合。
- `banners.*.pickupWeaponIds`：该卡池的 pickup 武器集合。

### 4.5 读取、校验与发布

管理 API 可采用以下边界：

- `GET /api/admin/gacha-config`：返回主数据生成的武器对照表、卡池列表、当前配置、内容哈希和校验结果。
- `POST /api/admin/gacha-config`：提交完整配置及编辑前内容哈希。

保存沿用现有管理平台的 Bearer Token 鉴权和乐观锁：内容哈希已变化时返回冲突，要求开发者刷新后重试。服务端收到配置后依次执行：

1. 用当前主数据重新生成武器和卡池对照信息。
2. 执行第 9 节的完整配置校验并构建所有卡池。
3. 将规范化 JSON 写入同目录临时文件，再原子替换 `gacha.json`。
4. 原子替换内存中的 Gacha 配置和候选池，使新请求一次性使用新版本。

发布 Gacha 配置不修改 `.bin.e`，也不触发客户端下载主数据。主数据热更新后，管理平台重新生成对照表并通过 `sourceMasterDataHash` 标记配置已过期：

- 新出现且可抽取的根武器自动按常驻处理，并进入所有卡池。
- 新出现但被主数据排除的根武器自动按活动处理，不进入卡池。
- 下一次发布前需要检查新增默认常驻武器，以及已经失效的武器、Costume 或卡池引用。

## 5. 卡池构建

对每个 Gacha ID，在服务端启动或成功发布新配置时构建一份不可变候选池：

1. 从主数据读取武器 ID、星级、进化状态以及武器与角色的关联关系。
2. 排除进化后形态和不属于 2、3、4 星的条目。
3. 排除所有 `event` 武器。
4. 加入全部 `standard` 武器。
5. 只加入该卡池 `limitedSets` 中的 `limited` 武器；其他限定集合的武器不得出现。
6. 根据是否关联角色以及星级，将候选武器放入六个组。
7. 将该卡池的 pickup ID 标记到其所在组。

未在 `banners` 中配置的 Gacha 按“仅常驻、无 pickup”处理。这样即使遗漏限定卡池配置，也只会导致限定武器不可抽取，不会泄漏到错误卡池。

## 6. 组内 pickup 概率

先选择随机组，再在组内选择武器。pickup 只改变所在组的内部概率，不改变六组的总概率。

设某组有：

- `P` 个 pickup 武器；
- `N` 个非 pickup 武器。

### 6.1 该组没有 pickup

所有武器等概率：

```text
P(武器 i | 组 g) = 1 / N
```

### 6.2 该组存在 pickup

pickup 集合合计占该组概率的 50%，非 pickup 集合合计占另外 50%。两个集合内部各自等概率：

```text
P(pickup 武器 i | 组 g)     = 1 / (2P)
P(非 pickup 武器 j | 组 g) = 1 / (2N)
```

单个武器的最终概率为：

```text
P(武器 i) = P(所属组 g) × P(武器 i | 组 g)
```

同一卡池的 pickup 可以分布在多个组中。每个包含 pickup 的组都独立执行一次 50% / 50% 分配，而不是让全卡池所有 pickup 合计占 50%。

如果某组存在 pickup，但没有任何非 pickup 武器，则无法满足两侧各占 50%。该配置必须校验失败，不得自动把 pickup 概率提高为 100%。

### 6.3 推荐的随机步骤

两阶段选择可以精确表达上述规则，无需为每件武器生成浮点权重：

1. 按整数 `groupWeights` 选择一个组。
2. 若组内无 pickup，则从全部候选中等概率选择一件。
3. 若组内有 pickup，则先等概率选择 pickup 或非 pickup 子集，再从所选子集中等概率选择一件。

生产环境随机源应在进程启动时安全播种，并支持在测试中注入确定性随机源。

## 7. 十连末位规则

十连的前 9 个位置使用普通组权重。第 10 个位置不删除 2 星权重，而是把每个 2 星组的全部权重转移给相同发奖类型的 3 星组；4 星组权重保持不变：

```text
W10(character_weapon_3) = W(character_weapon_3) + W(character_weapon_2)
W10(weapon_only_3)      = W(weapon_only_3) + W(weapon_only_2)
W10(所有 4 星组)         = W(对应 4 星组)
W10(所有 2 星组)         = 0
```

按当前基础权重，第 10 位的组概率为：

| 组 | 第 10 位概率 |
| --- | ---: |
| `character_weapon_4` | 2% |
| `weapon_only_4` | 3% |
| `character_weapon_3` | 5% |
| `weapon_only_3` | 90% |

选中组以后，仍使用第 6 节相同的组内 pickup 规则。因此末位只保证不出现 2 星，不额外保证 4 星，也不改变 pickup 在所属组内合计 50% 的规则。

单抽不会累计十连进度。如果接口一次请求多个完整十连，则每个十连批次的第 10 个位置应用该规则，例如第 10、20、30 个位置。

## 8. 推广页面与概率展示

推广页面必须由卡池已经构建完成的概率数据生成，不能再通过名称、目录或商店启发式规则猜测：

- 推广武器集合等于有效的 `pickupWeaponIds`。
- 无 pickup 的卡池返回空推广列表。
- 展示顺序使用 `pickupWeaponIds` 的配置顺序。
- 每个展示项应给出其所属组、该组概率、组内条件概率和最终单抽概率。
- 赠送角色的武器在推广信息中同时展示其关联角色；随机结果的身份仍以武器 ID 为准。
- 十连末位概率应单独标注，因为它与普通位置不同。

示例：某卡池在 `character_weapon_4` 组有 2 件 pickup 和 8 件非 pickup。该组普通位置概率为 2%，则每件 pickup 的最终概率为 `2% × 50% ÷ 2 = 0.5%`，每件非 pickup 的最终概率为 `2% × 50% ÷ 8 = 0.125%`。

## 9. 配置校验

配置发布失败时不得写入文件或替换当前内存配置，并应输出具体 Gacha ID、武器 ID 和失败原因。服务端启动时若没有可用的旧版本，则拒绝启用 Gacha。至少校验：

- 六组权重存在、均为非负整数，且总和大于 0。
- 发布时依据的 `sourceMasterDataHash` 与当前主数据一致；哈希不一致时必须先刷新对照表。
- 配置 ID 必须指向当前主数据中的根武器而非进化后形态；未配置 ID 自动视为常驻。
- 武器星级只能为 2、3、4 星，且主数据中存在对应武器。
- `availability` 只能是 `standard`、`event` 或 `limited`；限定武器只属于一个已定义的限定集合。
- 非限定武器不得填写 `limitedSet`，限定武器必须填写有效的 `limitedSet`。
- 主数据自动排除的活动武器不出现在配置页面或 `gacha.json` 中；手工设置的活动武器只作为活动覆盖保存，不会进入常驻、限定或 pickup 池。
- Gacha ID 存在于当前卡池目录；缺失卡池配置本身不是错误，按默认无 pickup 处理。
- pickup ID 不重复，存在于主数据中，并属于该卡池最终候选池。
- 限定 pickup 所属的限定集合与当前卡池匹配。
- 权重大于 0 的普通随机组不能为空。
- 十连末位中，2 星组权重转移后的对应 3 星组必须至少包含一件候选武器。
- 有 pickup 的组同时至少有一个 pickup 和一个非 pickup 候选。
- `character_weapon` 必须存在有效的关联角色；`weapon_only` 不得被错误标记为赠送角色。

主数据热更新后出现的新武器属于安全的特殊情况：旧配置可以继续运行，新可抽取武器自动成为常驻；管理平台提示配置基于旧版主数据，便于开发者检查是否需要改为活动或限定。已经被旧配置引用、但在新主数据中消失或关联关系失效的武器仍应报告为错误。

## 10. 抽取与发奖边界

一次抽取应先生成全部随机结果，再在同一用户事务中扣除消耗并发奖，避免部分扣款或部分发奖。

随机机制只返回：

```text
WeaponOutcome {
    weaponId
    bonusCostumeId?  // 仅赠送角色的武器存在
}
```

重复武器、重复角色、首次获得标记和转换材料仍交给现有发奖逻辑处理，不参与概率计算。

## 11. 验收标准

后续实现至少应覆盖以下测试：

1. 对照表只为根武器生成行，并能正确给出武器名称、关联 Costume 名称和星级符号。
2. 本地化名称缺失时显示 ID 占位，且名称不写入 Gacha 配置。
3. 任意卡池都包含常驻武器，不包含活动武器。
4. 限定武器只出现在匹配限定集合的卡池中。
5. 候选武器按发奖类型和星级正确进入六组。
6. 无 pickup 时，组内所有武器生成相同的精确选择权重。
7. 有多个 pickup 时，pickup 合计 50% 且彼此等概率；非 pickup 合计 50% 且彼此等概率。
8. pickup 横跨多个组时，每个组独立执行 50% / 50% 分配。
9. 十连前 9 位使用普通分布；第 10 位把两个 2 星组权重分别划入相同发奖类型的 3 星组，4 星权重保持不变。
10. 缺失 pickup 配置时按无 pickup 处理，并在管理平台明确显示默认状态。
11. 非法覆盖、非法 pickup、错配限定武器、空正权重组和全组 pickup 均使发布校验失败。
12. 内容哈希冲突不会覆盖其他开发者已经发布的配置。
13. 写文件或构建候选池失败时，磁盘和内存中的旧配置继续有效。
14. 主数据新增可抽取武器时，该武器自动按常驻进入现有卡池；开发者只需为活动或限定例外添加覆盖。
15. 推广列表、管理平台发布校验和实际抽取复用同一份候选池数据。
16. 使用固定随机源的单元测试能复现边界选择；额外的统计测试在合理误差内符合配置概率。

## 12. 实现构成

1. 从当前主数据、武器—角色关联和本地化资源生成武器与卡池对照信息。
2. 定义逐武器明文配置格式，完成加载、规范化、内容哈希和校验。
3. 在现有 `/admin/` 中增加 Gacha 页面及读取、发布 API。
4. 用显式获取类别替换现有基于目录、名称或商店的候选池推断。
5. 将随机流程改为“选择六组 → 组内 pickup 分流 → 等概率选择武器”。
6. 在十连批次末位把 2 星组权重转移给对应的 3 星组。
7. 让推广页面、管理平台发布校验和概率接口复用同一份已构建概率数据。
8. 补齐管理 API、配置校验、确定性随机和少量统计回归测试。
